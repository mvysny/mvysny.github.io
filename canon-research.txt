1. PRINTER FACTS  (from the post; don't re-derive)
-------------------------------------------------

model            Canon PIXMA TS5351  (advertises as Canon_TS5300_series)
mDNS hostname    246989000000.local     <- the printer's "Printer Name" field,
                                           OK menu -> System Information
IP               192.168.1.50 (DHCP - do not hardcode in queues)
MAC              74:38:B7:xx:xx:xx
serial           KMHH00159
cert             self-signed, CN=192.168.1.50, issuer CN=CanonIJProduct...,
                 RSA 2048 / SHA-256, valid 2018-01-01 .. 2037-12-31

Root cause: the printer's embedded TLS server sends alert 40 (handshake_failure)
when the ClientHello offers TLS 1.3. Take 1.3 out of the offer and it happily
does TLS 1.2 with ECDHE-SECP256R1 + AES-256-GCM. Secure renegotiation (RFC 5746)
really is missing, but that was a red herring - GnuTLS's default
%PARTIAL_RENEGOTIATION permits the initial handshake and IPP never renegotiates.
OpenSSL objected to the renegotiation thing; CUPS/GnuTLS never did.

3. THE ANSWER - CONFIRMED ON HOST
---------------------------------

*** client.conf IS the fix. Printing works. ***

    file:  /var/snap/cups/common/etc/cups/client.conf
    line:  SSLOptions MinTLS1.2 MaxTLS1.2

Confirmed on HOST by Martin, in this order:
  - cups.ipptool over ipps:// succeeds and retrieves printer attributes
  - printing works
  - ALL /etc/gnutls/config changes reverted first, so the snap client.conf line
    is the only remaining modification to the host OS

So the system-wide GnuTLS override was never necessary. The scoped fix is two
lines in one file inside the snap's own config tree, blast radius = CUPS only.

Mechanism: cupsd exports CUPS_SERVERROOT into every filter and backend it forks,
so the forked ipp backend resolves client.conf to the snap's copy, and
_httpTLSStart() reads cg->ssl_options after populating defaults from that file.
The backend honoring it is what makes printing (not just ipptool) work.

Why the original debugging missed it: the SSLOptions line was written to
/etc/cups/client.conf, which under a snapped CUPS no CUPS process ever opens.
Right lever, wrong file.

DURABILITY - verified by reading /snap/cups/current/scripts/run-cupsd:245-250.
Every cupsd start rewrites client.conf, but it PRESERVES foreign lines:

    touch client.conf
    ( cat client.conf | grep -v ServerName > client.conf.new || true ) && \
        echo ServerName $DOMAINSOCKET > client.conf && \
        cat client.conf.new >> client.conf && \
        rm -f client.conf.new

i.e. it strips ServerName, rewrites it as line 1, then appends everything else
back. The SSLOptions line survives, only reordered to sit after ServerName. And
it lives in $SNAP_COMMON, which is NOT versioned - so it also survives snap
refreshes to a new revision. Nothing to re-apply.

*** REGRESSION AFTER REBOOT - section 3 above is NOT settled. ***

After a reboot on HOST: cups.ipptool over ipps:// still WORKS, but printing does
NOT. So the durability reasoning above holds for the client path and says nothing
about the print path. The pre-reboot "printing works" and the post-reboot
"printing doesn't" may not even be about the same mechanism - see section 3b.


3b. THE REGRESSION - WHAT SPLIT ipptool FROM PRINTING
-----------------------------------------------------

Established: cups.ipptool honors /var/snap/cups/common/etc/cups/client.conf and
reaches the printer over ipps://. That is a libcups CLIENT running as Martin.
Printing involves two other processes - cups-browsed (long-running daemon) and
the ipp/ipps backend that cupsd fork+execs per job. ipptool proves nothing about
either.

Candidate explanations, in rough order of likelihood:

 (a) THE DEFAULT QUEUE FLIPPED BACK.  The queue that printed before the reboot
     may not be the queue jobs go to now. If the pre-reboot success was on a
     hand-made queue - especially a plain ipp:// one, which never does TLS at
     all - then client.conf was never load-bearing for printing, and after the
     reboot cups-browsed re-created its implicitclass queue and took the default
     back. This would explain the split perfectly.
     KEY UNKNOWN: which queue actually printed before the reboot? Static
     ipps://? Static plain ipp://? The auto-discovered implicitclass one?

 (b) mDNS NOT READY AT PRINT TIME.  A queue pointing at 246989000000.local
     depends on Avahi being up and multicast working when the job runs. Right
     after a boot that is a race. Failure mode is name resolution, not TLS -
     and it would look identical from the outside ("nothing prints").

 (c) THE BACKEND GENUINELY DOESN'T READ client.conf.  Possible, but note the
     snap's libcups has /var/snap/cups/common/etc/cups compiled in as
     ServerRoot, so the backend should find the file even with no environment
     help. If this is the answer, the error log will show a TLS alert from the
     backend specifically.

 (d) cups-browsed decided reachability at discovery time and cached a verdict.

The error log discriminates between these in one line:
    - "A TLS fatal alert has been received"     -> (c), TLS, backend not capped
    - "No suitable destination host found"      -> (a) or (d), cups-browsed
    - name/host resolution failure              -> (b), mDNS

DIAGNOSTIC SET TO RUN ON HOST (all of it, before theorising further):

    # what queues exist, what are their device URIs, which is default
    cups.lpstat -v
    cups.lpstat -t
    cups.lpstat -o                 # stuck jobs

    # did the config actually survive the reboot, and in what order
    cat /var/snap/cups/common/etc/cups/client.conf
    cat /etc/gnutls/config          # confirm still reverted, no tls1.3 line

    # the logs
    sudo tail -100 /var/snap/cups/current/var/log/error_log
    sudo tail -100 /var/snap/cups/current/var/log/cups-browsed_log

Then the clean separating experiment - a static ipps:// queue, bypassing
cups-browsed entirely (this is old TODO 4.2, which may never have been run in
exactly this form):

    sudo cups.lpadmin -p TS5351ipps -E \
         -v ipps://246989000000.local:631/ipp/print -m everywhere
    cups.lp -d TS5351ipps /etc/hostname

  - prints  => the backend DOES honor client.conf; the problem is which queue
               jobs go to, i.e. candidate (a)/(d), and the fix is queue
               management, not TLS
  - fails   => candidate (c): the backend does not honor client.conf, and the
               scoped fix does not extend to the print path

And to remove (b) from the picture, repeat with the IP instead of the mDNS name:

    sudo cups.lpadmin -p TS5351ip -E \
         -v ipps://192.168.1.50:631/ipp/print -m everywhere
    cups.lp -d TS5351ip /etc/hostname


3c. RESOLVED: HOST RUNS **TWO** CUPS DAEMONS (snap AND deb)
----------------------------------------------------------

This explains the ipptool-works/printing-fails split completely.

Observed on HOST:

    $ ps -ef | grep cupsd
    root  4137     1  /usr/sbin/cupsd -l                          <- DEB
    root  4158     1  /bin/sh /snap/cups/1238/scripts/run-cupsd
    root  4440  4158  cupsd -f -s /var/snap/cups/common/etc/cups/cups-files.conf \
                            -c /var/snap/cups/common/etc/cups/cupsd.conf   <- SNAP

    $ sudo ss -lptne 'sport = :631'
    LISTEN 127.0.0.1:631  cupsd pid=4137  cgroup:.../system-cups.slice/cups.service
    LISTEN [::1]:631      cupsd pid=4137

    $ sudo ss -lpx | grep cups.sock
    /run/cups/cups.sock                  cupsd pid=4137 + systemd pid=1 fd=98
    /var/snap/cups/common/run/cups.sock  cupsd pid=4440

=> the DEB cupsd owns port 631 and the canonical /run/cups/cups.sock.
=> the SNAP cupsd is in PROXY MODE: no TCP port, only its private socket.

THE CONSEQUENCE FOR THE BUG:
  cups.ipptool is a SNAP binary -> snap libcups -> snap client.conf, and when
  given an ipps:// URI it talks STRAIGHT TO THE PRINTER, bypassing every cupsd.
  That is why the snap client.conf capped it and it passed.
  Printing goes to the DEB cupsd, which forks the DEB backend
  /usr/lib/cups/backend/ipp -> apt libcups 2.4.16 -> /etc/cups/client.conf.
  That file is uncapped, so the print path still offers TLS 1.3 and dies.

  => the SSLOptions line is needed in /etc/cups/client.conf for PRINTING.
     The snap's copy only ever fixed snap clients. Both files, or the deb one.
     Caveats: $HOME/.cups/client.conf is tried first by BOTH libcups builds and
     never falls back, so check `ls -la ~/.cups/`; and the deb daemon needs
     `sudo systemctl restart cups`, which restarting the snap does not do.

PROXY MODE MECHANISM - verified by reading /snap/cups/current/scripts/run-cupsd:

  detection (lines ~130-140):
      [ ! -f /var/snap/cups/common/no-proxy ] && [ -r /etc/cups/cupsd.conf ]
    NOTE: keyed on a CONFIG FILE BEING READABLE, not on the deb daemon running.
    So `apt remove cups-daemon` without purging leaves /etc/cups/cupsd.conf
    behind and the snap stays in proxy mode forever, proxying to nothing. The
    script's own comment says to create the no-proxy file in that case.

  in proxy mode:
    - PORT is set empty -> cupsd.conf has every Listen/Port line stripped
    - DOMAINSOCKET = /var/snap/cups/common/run/cups.sock (the ALT socket)
    - client.conf gets `ServerName /var/snap/cups/common/run/cups.sock`
    - $SNAP_DATA/var/run/proxy-mode is touched
    - run-cups-browsed refuses to start cups-browsed while that file exists
    - cups-proxyd <snap socket> <SYSTEM_CUPS_SERVER> -l --logdir ... is spawned,
      mirroring the deb's queues into the snap's cupsd as proxy:// DeviceURIs
    - SYSTEM_CUPS_SERVER is parsed out of /etc/cups/cupsd.conf
      (Listen /socket | Port N | Listen *:N | Listen host:N), default
      localhost:631

  standalone mode, 631 already taken -> falls back to port 10631 plus the alt
  socket ("parallel mode"). Escape hatch: touch /var/snap/cups/common/no-proxy.

  on leaving proxy mode the script deletes leftover proxy:// mirrored queues.

DIAGNOSTIC VALUE:
  - `lpstat -v` vs `cups.lpstat -v` can show the SAME queue names; the snap side
    has proxy:// DeviceURIs. Queue names are not decisive, DeviceURIs are.
  - ls /var/snap/cups/current/var/run/proxy-mode  -> snap is only a proxy
  - snap's client.conf ServerName value tells you the mode:
        /run/cups/cups.sock                 -> standalone
        /var/snap/cups/common/run/cups.sock -> proxy (or parallel)

after it". Martin confirms HOST had BOTH the deb and the snap installed from the

CURRENT BEST HYPOTHESIS: the print that worked was reading
/etc/cups/client.conf - the DEB path, which is the correct one for the daemon
that actually owns printing - and that file was cleaned up during the "revert

On the VM /etc/cups/client.conf does not exist at all - the deb ships no such

NEXT ACTION: put SSLOptions MinTLS1.2 MaxTLS1.2 in /etc/cups/client.conf and
`sudo systemctl restart cups` (the DEB unit - restarting the snap does not
touch it). Check `ls -la ~/.cups/client.conf` first: libcups opens that one
first and never falls back.

NEW FINDING - SNAP MODE IS STICKY UNTIL RESTART.  Observed on the VM: the deb
was installed and started at 17:55 while the snap had been running since 16:11.
Result - deb cups + cups-browsed active, /etc/cups/cupsd.conf readable, and yet

`ServerName /run/cups/cups.sock`, snap cups-browsed still running (proxy mode

ALSO: with the deb installed the VM now has TWO of every CLI tool -

6. RESOLVED: 4.4, THE nm DISCREPANCY  (verified on the VM, binary level)
-----------------------------------------------------------------------

THE DISCREPANCY WAS AN ARTIFACT. Both libcups builds reference BOTH symbols:

    $ nm -D --undefined-only <lib> | grep -E 'priority|gnutls_set_default'
    snap: U gnutls_priority_set_direct  +  U gnutls_set_default_priority
    deb : U gnutls_priority_set_direct  +  U gnutls_set_default_priority

Two ways the old command hid that:
  - the DEB library is STRIPPED, the snap's is NOT. `nm -u` (no -D) on the deb
    lib prints nothing at all ("no symbols", .symtab absent); on the snap lib it
    works. So the same command yields 0 symbols vs 2.
  - a grep for `gnutls_priority` matches only gnutls_priority_set_direct, since
    the other symbol is gnutls_set_default_priority. That yields exactly 1 vs 1.
Either way the post's nm probe does NOT show a real snap/deb difference. Fix or
drop that probe; do not present it as evidence of anything.

WHAT _httpTLSStart ACTUALLY DOES  (objdump of the snap's unstripped libcups;
the snap lib being unstripped is what makes this readable):

  Both calls live in _httpTLSStart, and BOTH ARE UNCONDITIONAL:

    48d4d  gnutls_init(&http->tls, mode)     mode: http->mode==0 -> GNUTLS_CLIENT(2)
                                                   else          -> GNUTLS_SERVER(1)
    48d5f  gnutls_set_default_priority(...)  <-- no guard, client AND server
    ...
    4933c  gnutls_priority_set_direct(...)   <-- no guard, every path converges here

  => so the answer to 4.4 is "yes, it IS reached", BUT it is then OVERWRITTEN by
     gnutls_priority_set_direct on every single path. Functionally moot.
  => /etc/gnutls/config's `default-priority-string` (an [overrides] key that
     retargets gnutls_set_default_priority) is therefore INERT for CUPS - but
     NOT for the reason the post gives. The post says libcups never asks for the
     system default. It does ask, then discards the answer.

THE PRIORITY STRING CUPS BUILDS  (globals decoded from .data, strings from
.rodata, control flow from the disassembly):

    0x8e1a8 tls_options      default -1  (sentinel -> _cupsSetDefaults())
    0x8e1a4 tls_min_version  default  1  (_HTTP_TLS_1_0)
    0x8e1a0 tls_max_version  default  5  (_HTTP_TLS_MAX)

    version table @0x8c600 = { VERS-SSL3.0, VERS-TLS1.0, VERS-TLS1.1,
                               VERS-TLS1.2, VERS-TLS1.3, VERS-TLS-ALL }

    if !(tls_options & 8)      strlcpy "@SYSTEM,"      <-- 8 == NoSystem
                               strlcat "NORMAL"
    if tls_max_version > 4:    strlcat "+VERS-TLS-ALL" (or ":+VERS-TLS-ALL:+VERS-SSL3.0"
                               when min==0), then ":-"+table[i] for i < min
    else:                      strlcat ":-VERS-TLS-ALL", then ":+"+table[i]
                               for i = min..max
    tls_options & 1 ? ":+ARCFOUR-128" : ":!ARCFOUR-128"
    always ":!ANON-DH"
    tls_options & 4 ? ":!AES-128-CBC:!AES-256-CBC:!CAMELLIA-128-CBC:..." : ""

  SSLOptions token list (rodata, 0x730b8..): AllowRC4, AllowSSL3, AllowDH,
  DenyCBC, DenyTLS1.0, MaxTLS1.0-1.3, MinTLS1.0-1.3, NoSystem.
  Note AllowDH (bit 2) is NEVER TESTED in _httpTLSStart - ":!ANON-DH" is
  appended unconditionally. Dead option in the GnuTLS backend.

  So, concretely:
    default (no SSLOptions):
      @SYSTEM,NORMAL:+VERS-TLS-ALL:-VERS-SSL3.0:!ARCFOUR-128:!ANON-DH
    SSLOptions MinTLS1.2 MaxTLS1.2  (min=max=3):
      @SYSTEM,NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2:!ARCFOUR-128:!ANON-DH

THE INTERESTING CONSEQUENCE - and this is genuinely new for the post:

  The default string STARTS WITH "@SYSTEM," so CUPS *does* consult the system
  [priorities] SYSTEM definition as its base. But it then appends
  ":+VERS-TLS-ALL", which re-enables every TLS version. Later directives win in
  a GnuTLS priority string, so any version narrowing done via @SYSTEM gets
  clobbered. That is why priority-string-level overrides looked inert while
  `disabled-version = tls1.3` under [overrides] worked: [overrides]
  disabled-version is enforced BELOW the priority string and cannot be undone by
  ":+VERS-TLS-ALL". The post's "bites below the priority string" instinct is
  right; the "never asks the system" explanation is wrong.

  NOT MEASURED: the "later directives win / +VERS-TLS-ALL clobbers @SYSTEM"
  step is documented GnuTLS priority-string semantics, not something verified
  on this box - gnutls-bin is not installed and I did not install it. If the
  post is going to assert it, either install gnutls-bin and confirm with
      gnutls-cli --priority '<string>' --list
  (it prints the enabled Protocols), or word it as documented behaviour.

  Also note SSLOptions MinTLS1.2 MaxTLS1.2 is confirmed to produce an
  explicitly-enumerated, TLS1.2-only version set - so the scoped fix does not
  depend on the @SYSTEM question at all.

7. THE SSLOptions NO-OP - A PROVEN UPSTREAM CUPS BUG
---------------------------------------------------

SCOPE OF THIS SECTION, BEFORE ANYTHING ELSE:

  ESTABLISHED - the mechanism below, at the library level, on the VM, from
  source and from gnutls-cli. And on HOST: adding NoSystem made ipptool honor
  SSLOptions and complete a TLS 1.2 handshake with the printer.

  ALSO ESTABLISHED, 7.1 - printing works. Martin put the line in BOTH
  /etc/cups/client.conf and /var/snap/cups/common/etc/cups/client.conf and
  printed from GNOME. So it is the fix, not just a real bug that was hurting us,
  and none of section 3b's queue/mDNS candidates were load-bearing after all.

  ONE THING STILL NOT ISOLATED - both client.conf files were edited at once, so
  "the deb file is the one that matters for jobs" remains an inference from the
  process tree (deb cupsd forks the deb backend, which reads /etc/cups), not
  something separated by experiment. Fine for the post as long as it is not
  claimed as measured.

New fact from HOST (Martin): adding **NoSystem** to /etc/cups/client.conf made
ipptool finally honor SSLOptions, negotiate TLS 1.2 and connect to the printer.
So the working line is:

    SSLOptions NoSystem MinTLS1.2 MaxTLS1.2

Independent corroboration of the same symptom on a completely different distro:
https://github.com/NixOS/nixpkgs/issues/467175 - "unable to print after upgrade
to 25.11, A TLS fatal alert has been received", Canon TR4700, CUPS 2.4.14, and
the reporter's own guess names the culprit: OpenPrinting/cups PR #1105. It
worked on NixOS 24.05 (older CUPS) and broke on 25.11. Nobody in that thread has
found NoSystem; the issue is still open and untriaged.

THE MECHANISM, END TO END (every step below verified, see EVIDENCE):

 1. OpenPrinting/cups PR #1105 "tls-gnutls.c: Use system crypto policy if
    available", merged 2024-12-06, shipped in **CUPS 2.4.12** (2025-04-08). It
    is a one-line diff in cups/tls-gnutls.c:

        -  cupsCopyString(priority_string, "NORMAL", ...);
        +  cupsCopyString(priority_string, "@SYSTEM,NORMAL", ...);

    The author's stated reasoning: "GnuTLS supports fallback mechanism, so we
    can fallback to NORMAL if @SYSTEM is not defined on the system."

 2. THAT FALLBACK DOES NOT EXIST. In GnuTLS, a priority string starting with
    '@' goes through _gnutls_resolve_priorities(), and every keyword in the
    comma list is looked up **only in the [priorities] section of the system
    config file** (_name_val_array_value(system_wide_config.priority_strings,
    ...)). Built-in level names are not consulted there. So "NORMAL" after
    "@SYSTEM," is not the built-in NORMAL - it is a config-file keyword that
    almost nobody defines. If no keyword resolves, the function returns NULL.

 3. gnutls_priority_init2() turns that NULL into GNUTLS_E_INVALID_REQUEST, and
    gnutls_priority_set_direct() returns it without touching the session.

 4. CUPS DISCARDS THAT RETURN VALUE:

        gnutls_priority_set_direct(http->tls, priority_string, NULL);   // no ret

    Note the contrast with the gnutls_set_default_priority() call ~200 lines
    earlier in the same function, whose status IS checked and aborts on error.

 5. So the session silently keeps the priorities set by
    gnutls_set_default_priority() - i.e. the plain default, TLS 1.3 included -
    and *every* SSLOptions value is discarded. MinTLS, MaxTLS, DenyCBC,
    AllowRC4, the lot. No log line, no warning, nothing.

 6. Result on this printer: TLS 1.3 in the ClientHello, alert 40 from the
    Canon, "A TLS fatal alert has been received".

 7. SSLOptions NoSystem (bit 8, _HTTP_TLS_NO_SYSTEM) skips the "@SYSTEM,"
    prefix, so the string becomes plain "NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2:..."
    which resolves normally and IS applied. Which is exactly what Martin saw.

WHO IS AFFECTED: any distro whose GnuTLS system config has no
`[priorities] SYSTEM = ...` entry. Ubuntu/Debian's /etc/gnutls/config has only
an [overrides] section (disabled-version = tls1.0/tls1.1/dtls0.9/dtls1.0), so
Ubuntu is affected. Fedora/RHEL define SYSTEM via crypto-policies
(/etc/crypto-policies/back-ends/gnutls.config), which is why it works for the
patch author - he is Red Hat's CUPS maintainer. A Fedora-shaped assumption
compiled into everyone's libcups.

Still present in CUPS master and in libcups3 master (checked 2026-08-22), with
the return value still discarded. Affected releases: 2.4.12 .. 2.4.19 and up.

EVIDENCE (all on the VM, Ubuntu 26.04, GnuTLS 3.8.12-2ubuntu1.1):

  Installed gnutls-bin (this is a NEW change to the VM; nothing else changed).
  The decisive run, with GnuTLS's own debug log naming the failure:

    $ gnutls-cli -d 3 --priority '@SYSTEM,NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2' --list
    gnutls[2]: cfg: system priority /etc/gnutls/config has not changed
    gnutls[2]: resolved 'SYSTEM' to '', next 'NORMAL'
    gnutls[2]: resolved 'NORMAL' to '', next ''
    gnutls[2]: unable to resolve @SYSTEM,NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2
    gnutls[3]: ASSERT: ../../lib/priority.c[gnutls_priority_init]:3324
    Syntax error at: @SYSTEM,NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2

  Same string without the prefix works, and gives exactly the intended set:

    $ gnutls-cli --priority 'NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2:!ARCFOUR-128:!ANON-DH' --list
    Protocols: VERS-DTLS1.2, VERS-TLS1.2

  Define the missing keyword and the @SYSTEM form starts working, confirming
  that the missing [priorities] entry is the whole difference (temp file via
  GNUTLS_SYSTEM_PRIORITY_FILE, no host file touched):

    /tmp/x.conf:  [priorities]
                  SYSTEM = NORMAL
    $ GNUTLS_SYSTEM_PRIORITY_FILE=/tmp/x.conf gnutls-cli \
        --priority '@SYSTEM,NORMAL:-VERS-TLS-ALL:+VERS-TLS1.2:!ARCFOUR-128:!ANON-DH' --list
    Protocols: VERS-DTLS1.2, VERS-DTLS1.0, VERS-TLS1.2

  Source, quoted above: cups/tls-gnutls.c v2.4.16 lines 1509-1560; gnutls
  lib/priority.c 3.8.12 lines 2514-2620 (_gnutls_resolve_priorities) and 3313
  (the darg==NULL -> error path). The 3.7.3 copy of that function - the version
  in core22, i.e. the snap's GnuTLS - is byte-identical apart from formatting
  and one extra argument, so the snap behaves the same way.

  Also verified: NoSystem is documented, in both client.conf(5) and
  cupsd.conf(5), as "The NoSystem option disables applying system cryptographic
  policy." Reads like a security-weakening knob, gives no hint that without it
  the other thirteen SSLOptions keywords are thrown away. And unknown keywords
  in an SSLOptions line are ignored silently (cups_set_ssl_options() in
  usersys.c has no else clause), so a typo behaves the same as the bug.

BONUS BUG - the feature does not work even where @SYSTEM resolves. CUPS appends
":+VERS-TLS-ALL" whenever no MaxTLS is set, and later directives win:

    /tmp/y.conf:  [priorities]
                  SYSTEM = NORMAL:-VERS-TLS1.3
    $ ...gnutls-cli --priority '@SYSTEM' --list
    Protocols: VERS-TLS1.2, VERS-TLS1.1, VERS-TLS1.0, VERS-DTLS1.2, VERS-DTLS1.0
    $ ...gnutls-cli --priority '@SYSTEM,NORMAL:+VERS-TLS-ALL:-VERS-SSL3.0:!ARCFOUR-128:!ANON-DH' --list
    Protocols: ..., VERS-TLS1.3          <-- policy's version ban undone

  So a Fedora crypto policy that bans TLS 1.3 is silently overridden by CUPS's
  own default priority string. This also settles the "NOT MEASURED" caveat in
  section 6: later-directives-win is now measured on this box, not just
  documented.
